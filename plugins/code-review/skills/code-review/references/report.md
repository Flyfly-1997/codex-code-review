# 评审报告

首行使用 `**合并结论：<图标> <结论>**`，并给出三档确认数量。图标与结论按下表配对。结论之后写验证状态和静态审查边界。保留 `## 代码评审` 标题。图标用于合并结论和严重度标题。关闭、草稿、已评且无变化或仅需跳过的自动化 PR，给出原因即可。

| 结论 | 条件 |
| --- | --- |
| ✅ 可以合并 | 覆盖充分，0 高、0 中，列出确认的低严重度 |
| ⚠️ 修复后合并 | 0 高，至少 1 中 |
| ⛔ 合并前必须修复 | 至少 1 高 |
| 🚫 不建议合并 | 存在结构性高严重度问题，或先前高严重度问题仍未解决 |
| ❔ 无法判断 | 必要覆盖缺失，说明缺口，并照常报告已确认的问题 |

验证状态按实际计数，例如 `独立验证（N 条候选全部经 verifier）`、`部分独立验证（N 条经 verifier，M 条自复核）` 或 `未独立验证（low triage / 顺序自复核 / 无需复核的候选）`。覆盖缺失时不要输出「未发现问题」的完整覆盖措辞。

独立数量以实际工作者身份和审计结果为准。分别计数确认、拒绝和待证。行为发现的证据至少包括真实入口、触发条件和可见结果。把入口缺证据的候选列入「未解决」，并写明还需什么。

分级由复核证据决定。高包含明确错误结果、数据丢失/损坏、安全隐私、崩溃、功能不可达、既有修复回归、明确的规范违反和结构性风险。中包含特定条件下的用户可见错误及新增热路径开销。低包含冷路径成本、重复逻辑和被改成假话的纯措辞。行为契约按被掩盖的实际问题分级。

用准确的条件描述可见影响。说明哪些请求触发查询，哪些例外才触发模型或兜底。对恢复问题，分别描述已保存的数据、恢复时遗漏的后续动作和已存在的补偿。覆盖段给出实际检查过的跨文件路径以及候选裁剪数量，如有。

```markdown
**合并结论：⚠️ 修复后合并** — 0 个高严重度，1 个中严重度，0 个低严重度。
验证状态：独立验证（2 条候选全部经 verifier）。
仅代表本次审查：未检查构建、测试、运行时行为和审批状态。

## 代码评审：PR #<n> <title>

**改动概要**

- 3–5 条，说明改了什么、影响谁。

**🔴 高严重度（0）**

无

**🟡 中严重度（1）**

1. **[correctness]** [src/auth/token.ts:88](src/auth/token.ts#L88) — 一句话标题。
   - 影响：什么情况下影响谁。
   - 证据：具体代码、触发条件和调用链。
   - 建议：具体的最小修复。

**🟢 低严重度（0）**

无

**未解决**

- [path:line](path#Lline) — 还需要什么证据才能定论。没有则写「无」。

**审查范围**

- 目标：PR #<n>（`main` ← `<branch>`），head `<sha>`
- 变更：N 个文件，+X / −Y
- 覆盖：N 个分片中实际覆盖 K 个；M 条 DEEP 中 K 条已定论
- 未检查：构建、测试、运行时、审批状态

本次评审最多报告 32 条，实际报告 1 条。结论只来自代码阅读，没有跑测试，也没有在浏览器里走查，评审结果没有发到 PR 上。
```

编号跨档连续。规则类用「规则」引用实际阅读的规范路径、适用条文，再给「证据」和「建议」。已删除行属于 base 时在发现和链接中标明。使用相对仓库的链接并保留可读的锚点；公开 PR 评论用对应证据的完整提交 SHA。路径评审必须说明分支其余部分未审。报告用实际数字及发送状态；非 PR 的结尾省略 PR 发送场景。无确认问题且覆盖完整时，加一句「未发现问题」并指明确实检查过的规则和镜头。
